I decided to start with TigerNet. My understanding was that TigerBook was no longer active and that the newer version had recently updated authentication and stronger scraping restrictions. I have not independently confirmed the retirement or update dates. What I could see during the work was that authentication and access limits made collection much harder than I first expected.

The first issue was auth. Fully automated authentication was not possible because the login required approval through Duo Push MFA. I allowed attended authentication to move forward. That means the current approach does not satisfy the original requirement for fully unattended login. Credentials stay local and must never go into GitHub. Getting through login also did not guarantee that the directory requests would work. We ran into Cloudflare challenges and throttling after authentication.

Timing became the biggest challenge. I kept attempting faster approaches because collecting roughly 131k profiles takes too long when each profile needs several requests. We tried direct requests, browser collection, and multiple-browser experiments. Opening more browsers did not establish a separate request allowance. Increasing the configured request rate also gave much smaller gains than I expected. One Chrome test at six requests per second still completed about 0.19 profiles per second.

I also was not satisfied with the first CSV. It was difficult to read, and I was concerned about missing fields. I supplied the known field list as a minimum and asked for dynamic handling of additional fields. The export now includes the known columns and fields found during collection. I verified the field accuracy and coverage against the source.

One win is that progress is saved. We can stop and resume without collecting all the completed profiles again. The full scrape is running from the saved queue. The collection and export path works, and the remaining work is still substantial.

The latest saved extraction benchmark added 1,846 profiles in about 3,309 seconds, which is roughly 0.56 profiles per second. I am using 65 hours as a rough collection estimate at that pace. It could take longer if there are more MFA delays, cooldowns, interruptions, reconciliation work, or failed profiles to revisit. I have accepted this timing because the faster attempts kept reaching TigerNet's request restrictions. I did not find a complete-record workaround that the site accepted at a meaningfully higher sustained rate.

I found a conflict in the fast implementation while reviewing field coverage. The labelled sections were dynamic, but the extra header values still came from a fixed subset. That could leave out a new header field. The fixed subset has now been removed. The scraper compares each profile's permitted header response with its base response and includes matching visible values. The known field list controls the readable column order and makes the CSV easier to review. It does not limit the fields that can be collected. The active long-running process started before this revision, so the revised handler takes effect at its next normal restart or resume.

Reviewers will use their own TigerNet accounts. They do not need my account information. Their username and password remain in their local environment, and Duo approval happens during their own login. No credentials, sessions, databases, profile records, or CSV exports belong in the public repository.

I created a Google Sheets update structure with separate areas for run status, profile headers, field coverage, and final import checks. It currently contains no scraped profile rows. The data import, row reconciliation, and view permissions have to wait until the collection finishes. I also caught a size issue before import. At 131,890 rows and the currently observed 76 columns, the data would be slightly above Google Sheets' 10 million cell limit. I will recalculate this from the final CSV and split the data across linked Sheets if the final width still exceeds the limit. I will keep every profile and field.
